# Coffee PWA 生产运维手册

## 当前稳定基线

- 主分支：`foundation`。
- 前端：GitHub Pages `https://frankkiss.github.io/coffee-pwa/`。
- 同步模式：生产全局 `enabled`。
- 后端：Supabase Auth、Postgres、RLS、事务 RPC 和 Edge Functions。
- AI：`import-source` 与 `recommend-brew` 共享 `DEEPSEEK_VISION_API_KEY`。

本手册不授权生产变更。数据库迁移、Edge Function 部署、同步模式变化和全量数据恢复仍需各自明确批准。

## 每次发布前

1. 确认工作树、目标分支、目标提交和远端状态。
2. 审查变更范围，确认没有密钥、用户数据、私有备份路径或生产证据。
3. 运行前端测试、lint 和带非秘密值的生产构建。
4. Edge Function 变化运行 Deno 测试；migration 变化运行本地 Supabase reset 和数据库测试。
5. 对照 `supabase/migrations` 与线上 migration list，禁止凭文件名猜测线上状态。
6. 在生产 SQL Editor 原样运行只读 `supabase/sql/004_data_safety_preflight.sql`；它必须保留事务和最终 rollback。
7. 私下核对表计数、孤立关系、约束、RLS、异常值、同步代次和待处理状态；发现异常立即停止。
8. 下载并验证当前轻量 v2 备份。涉及恢复或高风险数据变化时另保留数据库级证据。

## 前端发布

只通过 `.github/workflows/deploy-pages.yml` 和复用的数据安全质量门发布，不上传本地 `dist`。确认部署 artifact 对应审查过的提交，GitHub Pages 路径、Manifest、Service Worker 和手机/电脑刷新正常。

发布后验证：登录、豆子读取、离线新增、恢复联网、Outbox 归零、另一设备拉取、最终字段一致、备份下载和同步状态。任何不明计数减少、重复写入或旧值复活都进入保护处理。

## Migration 发布

生产 migration 默认只增加表、列、索引、RPC 或未验证约束。应用前核对项目引用、备份、migration list 和预检；只应用已审查文件，按时间顺序执行。

命令失败时不自动重跑。先确认 migration 是否提交：未提交则依赖事务回滚并诊断；已提交但预检失败则保留新增结构、进入保护模式并编写新的前向修复 migration。不得用旧 schema、删除列或手工标记回退掩盖失败。

## Edge Function 发布

确认共享 Secret 存在但不显示其值。只部署受影响函数，不使用 `--no-verify-jwt`。部署后验证：认证成功、未认证拒绝、限流、请求上限、日志脱敏、结构化响应和规则降级；`import-source` 还必须验证 `url` 返回稳定 400 且没有网页请求。

可回退版本必须仍具备当前全部安全控制。没有经过审查的安全旧版本时，保持前端保护模式并发布前向修复，不得为了快速恢复而部署缺少认证、限流或输入边界的函数。

## 监控与停止条件

私下记录非内容型指标：发布提交、同步成功/重复/失败/待处理数量、代次、备份校验结果、Edge 状态码与延迟、客户端迁移或保护错误。不要记录行内容、完整 Prompt、令牌、密钥或私有备份路径。

以下任一情况立即停止扩展并准备保护发布：

- 数据丢失信号或无法解释的计数下降；
- 跨用户/RLS 失败；
- 备份校验和或恢复关系错误；
- 非预期代次变化、重复写入或旧设备自动覆盖；
- 本地迁移失败、Outbox 损坏或持续 needs-attention；
- 影响核心路径的持续 Edge 5xx。

预期的 400、401 或经过测试的 429 本身不是数据事故。

## 事故第一响应

1. 停止部署、扩展和不明重试。
2. 记录 UTC 时间、前端提交和模式、函数提交、最后成功阶段、错误码、受影响实体类型、pending 摘要和同步代次。
3. 保留所有设备 IndexedDB 和 Outbox；不要清站点数据、卸载 PWA，或让有待同步修改的设备退出登录。
4. 获取并验证事故时点备份和恢复前 v2 备份。
5. 优先使用前端保护模式阻止迁移、同步上传和写入，同时保留读取与导出。

绝不使用 `git reset --hard`、截断业务表、物理删除用户数据、删除 IndexedDB、回放旧 schema 或重置 migration history 作为事故捷径。

## 回退边界

- 前端回退：发布经过质量门的保护构建，不改变数据库。
- Edge 回退：仅部署预先审查且仍满足当前安全边界的函数版本。
- Migration 失败：保留已提交的新增结构，采用新的前向修复 migration。
- 数据问题：先比较只读预检和事故备份；可以明确识别时优先窄范围前向修复。

## 全量数据恢复

全量恢复是用户可见逻辑数据恢复，不是 schema 回滚。它始终需要针对选定 v2 备份校验和和最新影响预览的单独确认。

恢复前必须：验证备份、刷新 `full_rollback` 预览、成功下载并验证当前生产状态的恢复前轻量备份、显示增加/更新/复活/软删除影响，并取得明确确认。

恢复使用一个稳定 request ID 和备份校验和调用事务 RPC。响应丢失时只能用相同参数重试。成功后必须拉取新权威快照、采用新 `syncEpoch`、生成恢复后备份并重跑预检。其他设备的旧代次 Outbox 继续隔离，绝不自动重放。

重新开启写入属于新的发布决定，需要重新完成本地质量门、审查、设备验证、明确批准和监控。
