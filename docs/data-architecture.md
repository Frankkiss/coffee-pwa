# Coffee PWA 数据架构与安全契约

## 事实源和本地工作层

Supabase Postgres 是登录用户的云端事实源和唯一长期在线主库。IndexedDB 是本地工作层、最近服务器快照缓存和弱网队列，不是唯一耐久存储。UI 通过统一业务 Repository 读取本地合成视图，不得维护第二套队列或直接拼接另一份缓存。

云端数据表继续使用当前 Supabase 项目、Auth、Postgres、RLS 和 Edge Functions。仓库 migration 表示期望结构；任何生产变更前必须核对线上 schema、迁移历史、约束和异常计数。

## 离线写入和 Outbox

豆子、冲煮记录、用户模板和设置的每次保存必须在同一个 IndexedDB 事务中更新实体和 Outbox，事务提交后才通知 UI。任一步失败都不得出现“界面已保存但队列没有记录”。

Outbox 按 `userId` 隔离，保存稳定 mutation ID、设备 ID、实体类型、实体 ID、操作、完整 payload、基础 `syncEpoch`、状态、尝试次数和规范时间。设置不支持 delete；delete payload 必须是严格空对象；upsert 携带全部客户端可变字段，但排除所有权、主键、服务器时间和软删除字段。

所有持久化和 wire JSON 都视为不可信输入。当前用户的损坏记录必须进入保护状态并允许导出诊断恢复包，不能伪装成其他用户数据或自动删除。

## 同步顺序、锁和冲突

同一浏览器只允许一个活动 SyncManager。优先使用 Web Locks，不支持时使用带过期和持有者的 IndexedDB 租约。登录恢复、联网事件、本地提交、手动重试和 Realtime 信号都可以唤醒同步。

同步顺序是：取得跨标签锁、恢复遗留 `syncing`、读取并保守压缩 Outbox、标记发送中、调用原子批次 RPC、验证响应、确认已应用 mutation、拉取并验证服务器快照、原子替换快照与同步元数据。

`upsert → delete` 默认不能抵消；必须保留完整 upsert 和后续 delete。只有服务器确认的 `applied` 或 `duplicate` 才能确认对应及被覆盖的 mutation。网络、超时和 5xx 恢复为 pending 并有界退避；权限、字段和关联错误进入 `needs_attention`。

冲突采用记录级“最后成功提交到服务器者为准”，不做字段级合并，也不以设备本地时间决定胜负。Realtime 只是变化提示，权威数据必须重新通过一致快照 RPC 拉取。

每个异步边界后必须重新验证当前用户和运行 generation。登出、切换账号或停止同步后，旧用户的延迟回调不得确认、覆盖或删除新用户数据。

## 快照和代次

`get_sync_snapshot` 必须在同一个 PostgreSQL MVCC snapshot 中返回当前 `syncEpoch` 和全部实体集合。客户端把 RPC data 当作 `unknown`，完整验证顶层、UUID、时间、数字、枚举、关系和递归 JSON 后才替换本地快照；任意畸形内容都拒绝整份快照。

本地应用快照必须满足代次和时间单调性。低代次或同代次但早于当前基线的响应以 `STALE_LOCAL_SNAPSHOT` 拒绝，实体和同步元数据均保持不变。

全量恢复在服务器事务中递增 `syncEpoch`，隔离其他设备基于旧代次产生的 Outbox，防止恢复后被自动重放覆盖。

## 旧数据兼容

稳定客户端 ID 必须贯穿本地实体、Outbox、数据库、备份和恢复。旧 IndexedDB `snapshots`、`pendingMutations` 仍由自包含的 legacy migration raw reader 读取；删除旧运行时代码不得删除或升级这些物理 store。

旧数据中已有的剩余量、拼配组成、拼配说明和方式字段必须按原值迁移。缺失的新字段采用明确兼容默认值；非法值进入恢复保护，不能静默丢弃。读取时推断旧冲煮方式不等于自动回写。

## Postgres、RLS 和事务接口

所有用户数据都带 `user_id` 或等价用户主键并启用 RLS。策略同时限制读取和写入 `WITH CHECK`。RPC 从认证会话读取 `auth.uid()`，忽略或拒绝客户端伪造用户 ID。

批次 RPC 在单个事务中验证代次、幂等回执、时间格式、实体 schema、同用户外键和操作依赖，再用服务器时钟提交。结构性错误回滚整个批次。幂等回执只用于短期去重，不保存字段历史，清理失败不得影响业务写入。

`brew_logs.bean_id` 和 `ai_recommendations.bean_id` 必须指向同一用户的豆子。优先使用复合外键；任何线上修复采用可审查的新增或前向修复 migration，不自动删除异常数据。

RPC 优先使用调用者权限和 RLS。不得向 `anon` 或 `PUBLIC` 开放业务表；权限收紧必须等所有直接消费者迁移并单独审批。

## 备份 v2

默认轻量备份覆盖全部用户可见文字数据：豆子、冲煮记录、用户模板、已保存推荐、设置和必要来源记录，不包含图片、密钥、IndexedDB 缓存、Outbox、失败日志、回执或同步锁。

完整备份只在用户明确选择时加入经过限制和压缩的图片。导出必须带格式版本、生成时间、用户范围、实体集合和校验和。导入文件是不可信输入，必须限制大小、严格解析、校验版本、数字、时间、枚举、关系和校验和。

安全合并只增加、更新或复活备份中存在的实体，不删除云端额外数据。全量恢复必须先显示影响预览，成功下载并验证当前状态的恢复前轻量备份，再由用户输入明确确认；服务器在一个事务中软删除备份外数据、恢复备份内容、记录稳定请求回执并递增代次。

请求结果不确定时只能使用相同 request ID、模式和校验和重试。事务任一步失败必须全部回滚，不能逐表补做。

## 失败处理与不变量

- 退出登录前如有 pending、syncing 或 needs-attention 项，必须提示影响。
- “放弃并恢复云端版本”必须先取得完整有效快照，再在一个本地事务中删除目标 mutation、重算保护集合并应用快照。
- 任何数据丢失、跨用户结果、校验和错误、异常代次、重复写入或本地迁移失败都立即停止扩展并进入保护模式。
- 不得清除站点数据、删除 IndexedDB、截断业务表、用旧 schema 回滚，或用 `git reset --hard` 作为事故处理。
- migration 演进默认只增加；删除列、表、约束或兼容路径必须有独立设计、恢复验证和用户批准。
